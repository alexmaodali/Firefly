> 本篇为 Music 项目的设计总结
>
> 项目还在持续开发中

## 项目是什么

用 Flutter 做前端、Spring Boot 做后端的一个跨端音乐播放器，目标是支撑常见音乐平台的玩法。

**技术栈**：Flutter + Spring Boot + MyBatis-Plus + MySQL + Redis + ElasticSearch。

**功能蓝图**：登录注册、关注、私信、音乐推荐（热门/个性化/榜单）、播放界面（歌词滚动、评论、相关推荐）、ES 搜索、歌单（分类/详情/评论/相关推荐）、广场（发布带图随笔）、VIP 付费歌曲、音乐创作（AI+上传）、商城（扫码支付）。

> 目前先打透了 V1：登录注册 + 音乐列表 + 播放。

## 数据库设计

**用户表 user_info**：id（DBID）/ email（登录）/ password（登录密码）/ nickname（昵称）/ brief（个性签名）/ area（地域）/ gender（性别）/ birthday（生日）/ avatar（头像）/ status（0启用 1关闭）。

**歌曲表 song_info**：id / title（标题）/ artist（艺人）/ duration（时长）/ status（0启用 1关闭）。

设计上的一些取舍：

- 演唱者用字符串直接存，不拆艺人表——V1 够用就行，不强上复杂建模；
- `audio_url` / `cover_url` 只存文件名，真实磁盘路径由后端拼装，前端走统一文件接口取音频和封面；
- `lrc` 直接存歌词文本，省一次文件 IO 关联。

## 歌词检索

这是播放器里最有意思的一块：**给定当前播放到第几毫秒，怎么找到"此刻该高亮哪一句歌词"**。

### 存储

歌词用标准 LRC 格式：每条是一行 `[mm:ss.xx] 歌词文本`。后端把歌词原文直接存进 `song_info.lrc` 字段，前端进入详情页时拉取。

### 第一步：解析

前端在歌曲切换时解析一次，把 LRC 文本逐行拆开，用正则提取出每行的**起始时间**（转成毫秒）和**歌词文本**，得到一张有序表（大致这样）：

```dart
[
  { timeMs: 12000, text: '第一句' },
  { timeMs: 16000, text: '第二句' },
  // ...
]
```

这里有个易踩的细节：LRC 里时间可能是 `[mm:ss.xx]` 两三位小数，解析时要统一补齐位数、保证毫秒值不被小数截断，避免出现空字符串导致的空安全报错。

### 第二步：检索

播放时前端不停收到当前播放位置（毫秒）。所谓"歌词检索"，就是在这张有序表里找出 **"起始时间 ≤ 当前播放位置 的最后一行"**——因为它就是此刻正在唱、且还没唱完的那句。

这是个典型的有序表定位问题，朴素做法是线性扫一遍，简单且对几百行歌词完全够用。当"这次命中的行号"和上次不同时，就触发 UI 更新：把该行高亮、变大变亮，并让列表滚动到让这句落在屏幕中间。

### 第三步：滚动跟随

高亮行变化后，把歌词区滚到"目标行居中"的位置：用行号 × 行高算出偏移，减去一个常量让目标行处于可视区中部，再用带缓动曲线的动画平滑滚过去，避免生硬跳动。

> 一句总结：**解析展平 + 有序定位 + 高亮居中**，三个步骤把「播放进度 → 当前歌词行」这条链路打通了，既好懂，也足够流畅。
